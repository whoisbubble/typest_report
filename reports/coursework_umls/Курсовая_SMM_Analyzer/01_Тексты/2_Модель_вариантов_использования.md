# 2. Модель вариантов использования

Граница системы — веб-приложение SMM Analyzer, сервер API, обработчик заданий и хранилища. Пользователи взаимодействуют через браузер. Площадка не является актором базовой версии: файл загружает человек. Акторы: администратор, SMM-менеджер, аналитик, заказчик. Общий актор «Пользователь» объединяет вход и выход.

## Спецификации ключевых сценариев
### UC-01. Войти в систему
Актор: любой пользователь. Предусловие: активная учётная запись создана администратором.
Основной поток: ввод email/пароля → поиск идентификатора → проверка пароля и активности → создание сессии → открытие доступного рабочего пространства.
Альтернатива: неверные данные дают общее сообщение без раскрытия существования email; превышение лимита ограничивает попытки. Постусловие успеха: действующая сессия и событие входа.

### UC-02. Настроить кампанию
Актор: администратор. Предусловие: существует клиент.
Поток: указать название, цель, даты и бюджет → назначить сотрудников → сохранить черновик → активировать после проверки обязательных полей.
Ошибки: конец раньше начала, отрицательный бюджет, сотрудник другого агентства. Постусловие: кампания и назначения согласованы.

### UC-03. Зарегистрировать публикацию
Актор: менеджер, администратор. Предусловие: активная назначенная кампания.
Поток: указать площадку, URL, внешний ID, название и дату публикации → проверить уникальность → сохранить.
Альтернатива: видео уже зарегистрировано в агентстве — показать существующую доступную карточку либо сообщить о конфликте без раскрытия чужих данных.
Постусловие: карточка связана с одной кампанией; само видео не загружается.

### UC-04. Импортировать данные
Актор: менеджер, администратор. Предусловие: активная кампания, доступная публикация, JSON до 20 МБ.
Поток: выбрать файл → проверить доступ → сохранить файл и создать ImportJob → обработчик проверяет структуру и значения → одним коммитом сохраняет снимок и комментарии, меняет commentsRevision при изменении набора, завершает задание → пользователь видит сводку.
Альтернативы: неверный формат — FAILED с перечнем ошибок без частичного сохранения; повторный файл с тем же SHA-256 для публикации — вернуть существующее задание; временный сбой — повтор того же задания, максимум три попытки; исчерпание попыток — FAILED.
Постусловие: SUCCEEDED с числом созданных/обновлённых записей либо FAILED без изменения предметных данных. Исправленный файл образует новое задание.

### UC-05. Выполнить анализ
Акторы: менеджер, аналитик, администратор. Предусловие: есть комментарии, кампания не архивирована.
Поток: выбрать публикацию → зафиксировать неизменяемый входной набор и commentsRevision → создать AnalysisJob → обработчик вызывает AnalysisProvider → записывает результаты, категорию тональности и признаки подозрительности → завершает задание.
Альтернативы: нет комментариев — задание не создаётся; уже есть успешный результат той же версии данных и правил — используется он; данные изменились — завершённый результат сохраняется для исходной версии и помечается неактуальным при просмотре.
Постусловие: все результаты привязаны к заданию и версии входа; автоматический вывод не считается установленным фактом о ботах.

### UC-06. Учесть денежную операцию
Акторы: менеджер, администратор. Предусловие: активная кампания.
Поток: выбрать INCOME/EXPENSE → указать положительную сумму RUB, дату и описание → сохранить и записать аудит.
Альтернативы: неверная сумма — отклонить; конкурентное изменение — предложить обновить данные. Исправление создаёт новую запись со ссылкой replacesId, прежняя помечается REVERSED в одной транзакции.
Постусловие: в агрегат попадают только POSTED, дубликат запроса исключается idempotencyKey.

### UC-07. Подготовить и опубликовать отчёт
Создать черновик могут менеджер, аналитик и администратор; опубликовать — менеджер или администратор.
Предусловие: кампания не архивирована; задан корректный период.
Поток: собрать снимки метрик на границы периода, результаты анализа и финансовые агрегаты → сохранить внутренний черновик → проверить охват и выводы → сформировать клиентское представление без внутренних финансов и текстов комментариев → опубликовать неизменяемую версию.
Альтернативы: нет данных — показать пропуски, не подставлять нули; анализ устарел — блокировать публикацию, если этот анализ включён, до обновления; можно явно исключить блок анализа с указанием причины.
Постусловие: клиенту доступен только clientPayload опубликованной версии, привязанный к clientId кампании.

### UC-08. Просмотреть отчёт
Актор: заказчик. Предусловие: активная сессия и ClientUser.
Поток: открыть список → сервер выбирает опубликованные отчёты разрешённых клиентов → выбрать отчёт → получить clientPayload.
Альтернатива: чужой или неопубликованный отчёт — отказ без его содержимого.
Постусловие: данные не изменены.

UC-09 — управление пользователями, клиентами и назначениями; UC-10 — просмотр аудита. Доступны только администратору. UC-11 — просмотр статистики и результатов своих кампаний для сотрудников; UC-12 — выход с отзывом текущей сессии.
