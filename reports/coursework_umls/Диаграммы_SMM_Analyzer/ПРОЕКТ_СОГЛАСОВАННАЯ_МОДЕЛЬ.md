# SMM Analyzer — согласованная модель после аудита

Дата редакции: 21.10.2026. Этот файл вместе с пятью разделами в Теория и диаграммами 01–21 — актуальная основа будущего отчёта и разработки. Старый аудит описывает состояние ДО исправлений. Приложение, БД и инфраструктура пока проектируются, а не выданы за работающие.

## Предметная область и границы

Малое SMM-агентство ведёт клиентов, кампании и видеопубликации, импортирует показатели и комментарии, анализирует обратную связь, учитывает доходы/расходы и публикует отчёты. Администратор управляет доступом; менеджер — кампаниями, импортом и публикацией; аналитик — анализом и выводами; заказчик — чтением опубликованных версий своего клиента. Роли могут совмещаться.

Next.js — браузерный клиент и сервер страниц, NestJS — API, Node.js worker — отдельный процесс анализа, TypeORM — отображение PostgreSQL. Docker размещает процессы по схеме 21. Обучение ML не входит в курс; предусмотрен интерфейс будущего анализатора.

## Права и контроль целостности

Идентификатор пользователя берётся из проверенного сервером сеанса, а не доверенного поля формы. Аутентификация предшествует рабочей области. Пароли хранятся как криптографические хеши, соединения рабочих мест используют HTTPS. Каждая команда и запрос статуса проверяют активность пользователя, роль и доступ к целевой кампании. Знание requestId не даёт права прочитать чужой результат.

Менеджер может публиковать в назначенной кампании. Аналитик сохраняет выводы, но не публикует без отдельного полномочия. Заказчик читает только опубликованные снимки доступных клиентов. Клиентская can() нужна интерфейсу; окончательное решение принимает сервер. Администратор и технические роли БД не приравниваются к обычному заказчику. Учётная запись worker имеет отдельные ограниченные права; если процесс создаёт аудит от технического имени, используется выделенная техническая запись users с ролью analyst и active=false для запрета веб-входа. Учётные данные соединения worker с БД отдельные; это не пароль сотрудника и не обход guards через браузер.

## Идентичность и версии отчёта

Один логический reportId соответствует кампании и периоду: UNIQUE(campaign_id,period_from,period_to). reports содержит текущую рабочую информацию; report_versions — неизменяемые публикации. Название «рабочая версия» не означает, что запись reports уничтожается после публикации.

buildDraft создаёт рабочую запись, если её ещё нет, либо возвращает существующую без потери выводов. getDraft читает её. saveDraft(id,expectedRevision,text) сохраняет выводы условно и повышает revision. refreshDraft(id,expectedRevision) перечитывает актуальные метрики/финансы/анализ, сохраняет выводы и повышает revision. Если ожидание устарело, сервер возвращает конфликт; чужая правка не перезаписывается.

При публикации проверяются полномочия, непустые выводы, revision и source_revision. В той же транзакции окончательно сверяются версии, выбирается следующий номер version и сохраняются snapshot, draft_revision, request_id, published_by, published_at и аудит. Требуются UNIQUE(report_id,version), UNIQUE(report_id,draft_revision), UNIQUE(request_id). Номер публикации и revision редактирования — разные счётчики.

После публикации рабочая revision не изменяется только ради её повторного отправления. Новое редактирование/пересчёт повышает revision того же reportId. Прежние опубликованные строки никогда не обновляются. Новая публикация возможна после новой рабочей revision. Второй ключ для уже опубликованной revision получает явный ALREADY_PUBLISHED с указанием существующей версии; новую версию для той же revision создавать нельзя.

## Ключ запроса и восстановление результата

Клиент генерирует UUID до первого POST и сохраняет неизменные параметры команды. В diagrams 06–07 ключ называется requestId, в сигнатурах key, в БД request_id: это одно понятие. Ключ новой команды не переиспользуется для иного содержимого. При найденном ключе сервер сравнивает цель, инициатора и параметры: для импорта publication_id + file_hash, для публикации report_id + draft_revision + published_by. Несоответствие даёт конфликт.

При успешно сохранённом ключе повтор возвращает сохранённый итог, не запускает запись заново. Проверка повтора и ограничения выполняются атомарно. Конкурирующие запросы сериализуются по ключу и целевой сущности; предварительная проверка в интерфейсе не является защитой от гонки.

getImportStatus(key) читает import_jobs.request_id и result; getPublicationStatus(key) читает report_versions.request_id. Найденный итог доступен только авторизованному пользователю. Если записи ещё нет, возвращается notFound: транзакция могла не завершиться. Клиент может повторить **ту же** команду с тем же ключом. unknown означает, что исход пока не установлен. Тайм-аут не позволяет сообщить пользователю «точно ничего не записалось».

Для отвергнутой до начала записи команды отдельная запись результата не обязательна: повтор тех же параметров проходит проверку заново, не создавая ложной публикации. Гарантия возврата прежнего успешного результата относится к принятому и сохранённому ключу. Конфликт и отсутствие результата не смешиваются с успешной публикацией. После подтверждённой ошибки исправленная команда получает новый ключ.

Окончательная доменная запись и ключ успеха находятся в одной транзакции. Если COMMIT имеет неизвестный исход, возвращается unknown; нельзя выполнять компенсирующий «откат» поверх уже зафиксированной транзакции. Сначала выясняется статус по ключу. GET статуса не изменяет данные. Ошибка доступа к GET или недоступность сервера не являются доказательством отказа исходной команды: её исход остаётся неизвестным. OperationOutcome всегда содержит общий requestId; результат done/rejected относится к исходной команде, а не к успешности чтения статуса. Повторы ограничиваются задержкой и одним активным восстановлением на команду; при постоянной недоступности сети успех не гарантируется.

## Импорт и отсутствие дублей

Импорт выполняется серверным ImportService; worker не становится обязательным исполнителем импорта. При новой команде проверяются файл, права и входные значения. В транзакции блокируется целевая публикация, повторно проверяется ключ и выполняется upsert комментариев/метрик по естественным уникальным ключам. Итог и аудит успеха сохраняются с ключом.

request_id уникален в import_jobs. file_hash сохраняется для сверки/поиска, но **пара publication_id,file_hash больше не объявляется единственным универсальным ключом операции**: новый запрос тем же файлом не должен запрещать повтор после прежнего отказа. Дубли предметных данных исключаются UNIQUE(publication_id,external_id) комментариев и UNIQUE(publication_id,captured_at) метрик. Если данные не изменились, входная revision публикации не повышается.

import_status в этой редакции содержит терминальные completed/rejected. Временное ожидание интерфейса не равно строке running в БД. result — непустой JSON с известным итогом для сохранённой записи, включая counts/errors. При техническом откате запись успеха отсутствует; клиент получает rejected при подтверждённом отказе либо unknown, если исход не установлен. Технические ошибки без возможности записи не выдают фиктивный jobId.

## Входная revision анализа

publications.data_revision начинается с 1 и увеличивается при фактическом изменении метрик/комментариев в той же транзакции импорта. Даты posted_at и captured_at остаются датами источника, а не признаком новизны для системы. analysis_results.input_revision относится к data_revision конкретной публикации. Для одной публикации и входной версии действует UNIQUE(publication_id,input_revision).

Worker выбирает публикации, для текущей data_revision которых нет результата. Он читает согласованный набор и запоминает эту версию. Перед сохранением проверяет, что входная версия не изменилась. Если изменилась — результат отбрасывается и расчёт планируется для нового набора. В исходном проекте один worker, но условная запись и уникальность не допускают двойного сохранения результата одной версии.

Сохранение анализа не повышает publications.data_revision: собственный результат не запускает бесконечный самоанализ. При этом campaigns.revision повышается от изменения статистики, финансов или результатов анализа — она защищает актуальность отчёта. reports.source_revision хранит именно версию источников кампании. При формировании/обновлении отчёта чтение источников и source_revision согласовано; при публикации она проверяется атомарно с записью. Команды обновления источников и публикации используют согласованный порядок блокировок кампании/отчёта.

## Поля, ограничения и значения

Все FK обязательны и имеют ON DELETE RESTRICT. email нормализуется и уникален; roles — непустой массив значений admin/manager/analyst/customer без повторов. Связующие таблицы имеют составные PK. Для таблиц с историей физическое удаление блокируется ссылками; отдельный бизнес-сценарий архивирования кампаний здесь не заявляется без нужных полей.

- campaigns: ends_on >= starts_on, budget >= 0, revision >= 1.
- publications: UNIQUE(platform,external_id), data_revision >= 1.
- financial_entries: amount > 0, kind = income/expense.
- metric_snapshots: UNIQUE(publication_id,captured_at), views/likes/reposts >= 0.
- comments: UNIQUE(publication_id,external_id).
- import_jobs: UNIQUE(request_id), status = completed/rejected, result содержит сохранённый итог.
- reports: UNIQUE(campaign_id,period_from,period_to), period_to >= period_from, revision/source_revision >= 1.
- report_versions: UNIQUE(request_id), UNIQUE(report_id,draft_revision), UNIQUE(report_id,version), version/draft_revision >= 1.
- analysis_results: UNIQUE(publication_id,input_revision), input_revision >= 1, 0 <= score <= 1; sentiment = positive/neutral/negative/mixed.

jsonb в отчёте — осознанный воспроизводимый снимок, не замена всем таблицам. События аудита содержат actor_id, действие, цель и время. Составные ограничения, транзакции, разрешения технических ролей и резервное копирование нужно реализовать при написании кода; изображение диаграммы само их не исполняет.
