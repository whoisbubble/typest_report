# 5. Модель реализации SMM Analyzer

Материал для пояснительной записки и подготовки к защите. Это проект будущей системы: серверы, контейнеры и программный код пока не созданы. Схемы 19–21 дополняют предыдущие модели, а не заменяют их.

## Что объясняют эти диаграммы

По [лекции о компонентах Анисимова](https://sites.google.com/site/anisimovkhv/learning/pris/lecture/tema15/tema15_2), компонентная модель показывает физические части программного обеспечения и их зависимости. Здесь подготовлены оба представления: структура исходных модулей и исполняемый состав.

По [лекции о развёртывании](https://sites.google.com/site/anisimovkhv/learning/pris/lecture/tema15/tema15_3), модель размещения связывает исполняемые компоненты с вычислительными узлами и каналами обмена. Поэтому на схеме 21 нет файлов TypeScript: они относятся к схеме 19.

Все решения о конкретных папках, Docker, Nginx, протоколах и составе серверов ниже — принятые проектные решения SMM Analyzer, а не готовая конфигурация из лекций. Белый фон, обычный шрифт и ручная разводка линий продолжают оформление сборника.

## 19. Структура компонентов исходного кода

![Структура исходного кода](../PNG/19_CMP_source.png)

### Как читать элементы

Прямоугольник с маленьким значком компонента обозначает программный компонент. `«source»` уточняет, что это исходный код. Здесь несколько связанных файлов объединены в один компонент по папке; отдельный класс предполагается хранить в отдельном `.ts`-файле. Это помогает показать систему без десятков мелких прямоугольников.

Штриховая линия с открытым наконечником — зависимость. Её читают **от использующего компонента к используемому**. Например, `apps/web → packages/contracts`: веб-клиент использует типы интерфейса и DTO. Это не передача HTTP-запроса между запущенными серверами.

| Компонент | Назначение и связь с предыдущими моделями |
|---|---|
| `apps/web` | Next.js, страницы и клиентские модели из схемы 14: SessionState, WorkspaceModel, CampaignViewModel, ImportViewModel, ReportViewModel |
| `apps/api` | HTTP-контроллеры NestJS, аутентификация, guards и вызов прикладных сценариев; контроллеры не содержат весь алгоритм сценария |
| `apps/worker` | Отдельная точка запуска фонового процесса; вызывает прикладной анализ публикаций |
| `packages/contracts` | ApplicationApi и типы запросов/ответов из разбора 14; общие соглашения клиента и сервера |
| `packages/application` | ImportService, ReportService, AuthorizationService, AnalysisService; здесь находятся методы, которым соответствуют деятельности 17–18 |
| `packages/domain` | Доменные классы, ограничения и расчёты; интерфейс будущего анализатора |
| `packages/persistence` | TypeORM-сущности, отображение доменных объектов, репозитории, миграции модели БД 16 |
| `ops/` | Файлы сборки, запуска, прокси и резервного копирования. На схеме специально нет стрелок ко всем контейнерам: это конфигурация среды, а не импорт TypeScript-модулей |

Декомпозиция слоистая: HTTP-контроллеры вызывают прикладные сервисы, сервисы используют доменные правила и слой хранения. Конкретные репозитории передаются сервисам через механизм внедрения зависимостей (DI) NestJS. Стрелка к persistence показывает принятую зависимость слоя приложения от слоя хранения; здесь не заявляется строгая гексагональная архитектура.

Доменный Campaign и объект CampaignEntity для TypeORM имеют разные обязанности: первый выражает правила предметной области, второй — отображение в таблицу. Это не две разные кампании в базе. Domain и persistence не должны импортировать веб-страницы.

Контракт ApplicationApi реализуется HTTP-адаптером в клиентском приложении. Общие DTO можно импортировать в оба приложения как типы; секреты и код репозиториев в браузерную сборку не включаются. На схеме показаны основные зависимости уровня папок, а не полный граф всех импортов.

Примеры будущих файлов:

| Класс/сценарий | Планируемый исходник |
|---|---|
| ImportViewModel | `apps/web/src/models/import-view-model.ts` |
| ApplicationApi | `packages/contracts/src/application-api.ts` |
| ImportController | `apps/api/src/import/import.controller.ts` |
| ImportService | `packages/application/src/import/import.service.ts` |
| ReportService | `packages/application/src/report/report.service.ts` |
| Campaign | `packages/domain/src/campaign.ts` |
| CampaignEntity | `packages/persistence/src/entities/campaign.entity.ts` |
| Запуск обработчика | `apps/worker/src/main.ts` |

Это имена для будущей разработки, а не утверждение о существовании этих исходников.

## 20. Состав исполняемых компонентов системы

![Исполняемые компоненты](../PNG/20_CMP_runtime.png)

Здесь показано то, что участвует в работе системы после сборки. Граница компонента не обязательно равна компьютеру: на сервере могут одновременно работать Nginx, Next.js, API и worker. Их размещение раскрывает следующая схема.

Внутри компонентов явно подписаны предоставляемые и требуемые интерфейсы. Интерфейс — договор о доступных операциях. `REST / JSON` означает HTTP API с сообщениями JSON; `PostgreSQL / SQL` — доступ к СУБД по её протоколу. Для интерфейсов использовано текстовое представление в секциях компонентов: отдельные кружки и сокеты на этой схеме не применяются.

**Стрелки — зависимости, а не поток данных:** backup зависит от PostgreSQL, хотя дамп при чтении поступает из БД в backup. Для ответов не рисуется обратная стрелка: они входят во взаимодействие через тот же интерфейс.

### Как проходит пользовательский запрос

1. Браузер загружает страницы и JS через единую HTTPS-точку входа Nginx.
2. Nginx направляет `/` и ресурсы в Next.js, `/api/*` — в NestJS, снимая внешний префикс `/api` согласно конфигурации.
3. API устанавливает личность пользователя, проверяет полномочия и принадлежность кампании, затем вызывает прикладной сервис.
4. Сервис работает с PostgreSQL через TypeORM. Результат возвращается пользователю по тому же каналу.

Пользователь определяется по проверенному сервером сеансу. Конкретная реализация сеанса и способ хранения токена выбираются при реализации. В проекте предусмотрены хеши паролей, проверка активного пользователя, роли и назначения на кампании. Одного скрытия кнопок в браузере недостаточно.

### Зачем отдельный worker

Worker выполняет анализ публикаций по расписанию, чтобы длительные расчёты не занимали HTTP-запрос. В начальном проекте достаточно одного экземпляра. Он читает сохранённые комментарии и метрики, записывает analysis_results. ML не обучается: интерфейс анализатора позволяет позднее подключить отдельную реализацию для ВКР; до неё возможны описательные расчёты и правила.

Для этой топологии отдельный брокер сообщений не требуется. API и worker используют PostgreSQL. Worker выбирает публикации без результата для текущей publications.data_revision; analysis_results.input_revision хранит именно её. Перед записью повторно проверяется входная версия. Собственный результат анализа не меняет data_revision, но меняет campaigns.revision для актуальности отчётов. Точные правила — в [согласованной спецификации](../ПРОЕКТ_СОГЛАСОВАННАЯ_МОДЕЛЬ.md).

**Это не перенос импорта из диаграммы 17 в фоновую очередь.** Сам метод ImportService сохраняет набор данных и возвращает результат согласно уже принятой деятельности. Анализ — последующая отдельная операция. Когда анализ изменяет исходные сведения для отчёта, revision кампании повышается, чтобы схема 18 могла обнаружить устаревший черновик.

### Где отчёты и копии

Черновики и опубликованные снимки находятся в reports и report_versions PostgreSQL, как в схеме 16. Отдельное файловое хранилище PDF здесь не добавляется. Архив резервных копий — другое назначение: восстановление БД после потери данных.

Резервное копирование — отдельный исполняемый служебный компонент: планировщик запускает pg_dump, дамп шифруется и передаётся по SFTP. Опубликованные отчёты не извлекаются из этого архива при обычной работе пользователя.

## 21. Общая диаграмма развёртывания

![Развёртывание](../PNG/21_DEP_system.png)

### Что означает графика

- **Куб `«device»`** — вычислительный узел. Указаны рабочие места, сервер приложений, сервер БД и отдельное хранилище копий.
- **Вложенный прямоугольник** — установленный компонент. Вложенность отвечает на вопрос «где это работает».
- **`«executionEnvironment»`** — среда выполнения: браузер исполняет клиентский JS. Node.js и Docker подписаны у соответствующих серверных компонентов и узлов.
- **`«executable»`** — запускаемый служебный модуль; **`«artifact»`** — сохраняемый результат, здесь архив файлов.
- **Линия без стрелки** — канал обмена. На ней подписаны протокол и порт; двусторонний обмен не требует двух противоположных стрелок.
- **`[1..*]`** — один или несколько экземпляров рабочих мест. Точная численность сотрудников и клиентов пока не задана.

Это проект для одного развёртывания малого агентства, без кластеров и реплик. Все роли используют одну браузерную программу; доступные функции определяет серверная авторизация. Заказчик видит только доступные ему клиентские данные и опубликованные версии.

### Принятые места размещения

| Узел | Что установлено | Причина |
|---|---|---|
| Рабочие места | Браузер, загружаемые страницы и клиентский JS | Не требуется установка настольного клиента |
| Сервер приложений | Docker Engine, контейнеры Nginx, Next.js, NestJS, worker | Единое развёртывание кода приложения при раздельных процессах |
| Сервер БД | PostgreSQL, постоянный том pgdata, среда pg_dump с планировщиком | Данные не зависят от жизненного цикла контейнера приложения |
| Хранилище копий | SFTP-сервис и зашифрованные дампы на отдельном узле | Потеря диска основного сервера не уничтожает единственную копию |

### Каналы и ограничения доступа

| Участники | Интерфейс | Ограничение |
|---|---|---|
| Браузер → Nginx | HTTPS, TCP 443 | Единственная публичная точка входа приложения |
| Nginx ↔ Next.js | HTTP, TCP 3000 | Только закрытая Docker-сеть одного сервера |
| Nginx ↔ API | HTTP, TCP 3001 | Только закрытая Docker-сеть; публично доступен маршрут HTTPS `/api/*` |
| API/worker ↔ PostgreSQL | Протокол PostgreSQL поверх TLS, TCP 5432 | Межсерверное закрытое соединение; разрешены адреса сервера приложений |
| pg_dump ↔ PostgreSQL | libpq, TCP 5432 | Локальная служебная сеть сервера БД; отдельные права чтения |
| Среда копирования ↔ архив | SFTP поверх SSH, TCP 22 | Разрешён сервер БД и отдельная служебная учётная запись |

Канал сервер приложений — сервер БД на рисунке объединяет соединения API и worker: это один сетевой путь, но разные процессы и подключения. Внутри сервера БД библиотека libpq используется pg_dump, а не пользовательским браузером. Обратная передача ответов подразумевается.

Терминация TLS находится в Nginx. HTTP внутри одного доверенного хоста — принятое упрощение проекта, не рекомендация открывать эти порты в Интернет. PostgreSQL и SFTP не публикуются для рабочих мест. Межсетевой экран допускает только перечисленные назначения; административные SSH-подключения находятся вне рассматриваемых пользовательских сценариев.

### Резервное копирование и целостность

pg_dump формирует согласованную логическую копию. Проектное допущение: один дамп ночью с хранением последних 14 успешных копий. Реальные RPO/RTO и объём диска согласуются с агентством после появления объёма данных; сроки не выданы за требования преподавателя. Шифрование выполняется до отправки, ключ восстановления хранится отдельно от архива; проверяются контрольная сумма и успешное завершение передачи. Удаление старой копии допустимо после сохранения новой.

В план эксплуатации входит пробное восстановление в изолированную БД. Сам факт наличия файла ещё не доказывает возможность восстановления. На текущем этапе это проектная процедура: реальное копирование и восстановление не запускались.

PK/FK, CHECK/UNIQUE и транзакции из модели 16 защищают данные при записи. Для публикации сохраняются проверки revision и неизменяемая версия отчёта из схемы 18. Аудит действий находится в PostgreSQL, резервные копии дополняют эти меры, но не заменяют их. Runtime-роли БД не должны иметь права изменения схемы; миграции выполняются отдельно.

### Сборка и воспроизводимость

| Исходные компоненты 19 | Результат для схем 20–21 |
|---|---|
| apps/web + contracts | Серверная сборка Next.js и клиентский JS-пакет |
| apps/api + application + domain + persistence + contracts | Образ API NestJS |
| apps/worker + application + domain + persistence | Образ фонового обработчика |
| ops/nginx.conf | Конфигурация Nginx |
| ops/backup.sh | Служебный запуск pg_dump, шифрование, SFTP |
| persistence/migrations | Миграции таблиц PostgreSQL |
| ops/compose.yaml + Dockerfile.* | Параметры сборки и запуска контейнеров на соответствующих узлах |

Артефакты проектируются с общим тегом релиза `smm-web:<release>`, `smm-api:<release>`, `smm-worker:<release>`; `<release>` — обозначение будущего значения, а не существующая версия. Конкретные версии Node.js, PostgreSQL и базовых образов фиксируются при реализации вместе с lock-файлами и digest. Они намеренно не выдуманы в диаграмме. Для двух серверов используются отдельные конфигурации запуска, а не иллюзия, что один Docker Compose автоматически управляет удалёнными компьютерами.

## Как объяснить на защите

«Диаграмма 19 отвечает, из каких исходных модулей состоит проект и какие зависимости между ними. Диаграмма 20 показывает состав работающей системы и её интерфейсы. Диаграмма 21 показывает, на каких компьютерах размещены эти компоненты и по каким протоколам они взаимодействуют. Браузер не подключается к БД. Запросы проходят через Nginx и NestJS, фоновые расчёты выполняет worker, а резервные копии хранятся отдельно от основной БД».

Если спрашивают о стрелках: на 19–20 это зависимости «использует», на 21 линии без стрелок — каналы обмена. Компонент — часть программы; узел — место её выполнения; интерфейс — набор возможностей для взаимодействия. Куб не является таблицей БД, а компонент не является классом.
