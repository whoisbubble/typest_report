## 13–14. Клиентские классы

![Логические классы](../PNG/13_DES_client_logical.png)

![Физические классы](../PNG/14_DES_client_physical.png)

Прямоугольник имеет секции имени, атрибутов и операций. `−` — private, `+` — public. Сплошная стрелка показывает навигацию по хранимой ссылке. Кратность 1 у API означает один интерфейсный объект у формы; 0..* у форм допускает совместное использование адаптера. Рабочая область открывает 0..1 экземпляра каждой модели. Состояние сеанса относится к одной рабочей области. Штриховая стрелка с пустым треугольником от HttpApplicationApi к ApplicationApi — реализация интерфейса, а не зависимость и не наследование React-компонента.

Модель кампании хранит CampaignDto. Модель импорта хранит незавершённый запрос, модель отчёта — черновик и исходные параметры публикации. saveFindings сохраняет данные на сервере. PublishedReportsModel читает опубликованные версии для заказчика. ReportDraft закрывает поля и открывает операции чтения/проверки. API возвращает данные, а HTTP-адаптер создаёт из DTO объект ReportDraft с методами.

Это классы **основных рассматриваемых сценариев**, а не полный реестр всех вспомогательных форм системы. Учётные записи, справочники и финансовые экраны остаются отдельными разделами общего контекста. Размещение кода соответствует компонентам 19: модели и HTTP-адаптер — apps/web, контракт и DTO — packages/contracts. TypeScript interface описывает требования, а не содержит готовую реализацию.

Реализация HttpApplicationApi обязана поддерживать все операции контракта; в её секциях показаны только собственное состояние и общий приватный механизм HTTP-запроса. Сигнатура request<T> — сокращённое представление общего механизма; параметры метода HTTP, тела и заголовков уточняются в коде. В Drawio угловые скобки generic-типов сохранены как текст.

### Вспомогательные типы

| Тип | Определение |
|---|---|
| UUID | `type UUID = string` |
| UserRole | `admin / manager / analyst / customer` |
| Permission | Полномочия `campaign.write`, `import.execute`, `report.edit`, `report.publish`, `report.read` для этой модели |
| Section | Разделы `campaigns / imports / reports / analytics / access / customer`; финансы входят в группу данных |
| Period | `{from: string; to: string}`, календарные даты ISO YYYY-MM-DD |
| CampaignInput | `{id?: UUID; expectedRevision?: number; clientId: UUID; name: string; goal: string; startsOn: string; endsOn: string; budget: string}` |
| CampaignDto | Данные кампании с обязательными `id`, `revision: number` |
| PendingImport | `{key: UUID; publicationId: UUID; fileHash: string; file: File|null}` |
| PendingPublication | `{key: UUID; reportId: UUID; expectedRevision: number}` |
| ImportResult | `{jobId: UUID; requestId: UUID; imported: number; errors: string[]}` |
| ReportDto | `{id: UUID; reportId: UUID; version: number; draftRevision: number; publishedAt: string; snapshot: Record<string,unknown>}`; id — ID опубликованной версии |
| OperationOutcome<T> | Общий `requestId: UUID` и объединение `{state:'done'; value:T}`, `{state:'rejected'; errors:string[]}`, `{state:'unknown'}` и `{state:'notFound'}` |
| ImportOutcome | `OperationOutcome<ImportResult>` |
| PublishOutcome | `OperationOutcome<ReportDto>` |

`Promise<T>` — асинхронное получение значения, `File` — стандартный браузерный тип. Денежные значения передаются строками. После чтения исхода `done` клиент показывает успех; rejected означает подтверждённый отказ. unknown — исход неизвестен. notFound допустим у чтения статуса и не доказывает отсутствия выполняющейся транзакции.

buildDraft создаёт либо читает отчёт кампании за период. getDraft читает существующую рабочую версию; refreshDraft пересчитывает показатели с ожидаемой revision и сохраняет выводы аналитика. saveDraft меняет выводы с проверкой revision. Это устраняет тупик, при котором устаревший отчёт можно отклонить, но нельзя обновить.

Основа: [Анисимов, §§14.2–14.3](https://sites.google.com/site/anisimovkhv/learning/pris/lecture/tema14/tema14_2). Конкретный веб-стек и контракт — проектные решения SMM Analyzer.

## 15–16. Одна модель БД, три согласованных фрагмента

Рисунки 15 и 16 содержат фрагменты A–C одной модели. Чтобы отчёт не превращался в нечитаемый плакат, сохранены и отдельные изображения каждого фрагмента. `«reference»` — поясняющая метка повторного показа того же класса, **не отдельная таблица и не стандартный специальный вид связи UML**. У повторного класса показан только ключ; полный набор атрибутов дан в его основном фрагменте.

Во всех фрагментах проведены сплошные ассоциации; 1 и 0..* находятся у своих концов. В физической модели FK обозначен у поля; соединяется класс-таблица, а не рисуется зависимость. Отношение RESTRICT — правило удаления и вынесено в общую подпись. Операции таблицам не приписываются: поведение находится в сервисах.

### C. Финансы и отчёты

![Логическая БД C](../PNG/15_DES_db_logical_C.png)

![Физическая БД C](../PNG/16_DES_db_physical_C.png)

Отчёт — стабильный логический объект кампании за период, содержащий текущую рабочую версию. Каждая опубликованная запись хранит draft_revision, номер версии, ключ запроса, автора и неизменяемый снимок. UNIQUE(report_id,draft_revision) не допускает второй снимок одной и той же рабочей revision. Финансовая операция относится к кампании и содержит направление, положительную сумму и дату.

CHECK/UNIQUE, перечисления и правила конкурентных изменений полностью заданы в согласованной спецификации. Это проект схемы, миграции ещё не исполнялись. В обеих моделях 14 сущностей и 16 отношений; повторные reference-блоки не увеличивают число сущностей.

## 17–18. Деятельности методов

![Импорт](../PNG/17_ACT_import.png)

![Публикация](../PNG/18_ACT_publish.png)

Точка — начало, скруглённый блок — действие, ромб с текстом — решение, пустой ромб — слияние альтернатив, точка в окружности — конец. Каждому из трёх решений соответствует своё слияние. У исходов записи три несовместимых условия: подтверждённая фиксация, подтверждённый откат и неизвестный итог. Последний возвращает unknown, а не притворяется откатом.

После проверки личности и привязки ключа ищется сохранённый итог. Найденный результат возвращается без новой записи. Для новой команды выполняется проверка. Недопустимая команда даёт подтверждённый отказ. Допустимая — атомарную сверку и запись. Повторная проверка ключа, актуальности и доступа находится **внутри транзакционной границы**, а не только до неё. Реальное состояние БД защищают ограничения и условная запись/блокировки, а не нарисованная проверка сама по себе.

ImportService.importData(actor, publicationId, file, key) сохраняет набор, итог запроса и аудит; ReportService.publish(actor, reportId, expectedRevision, key) фиксирует снимок, ключ и аудит. Оба возвращают соответствующий OperationOutcome. GET статуса не выполняет повторную запись.

Дорожки не добавлены: это внутренние методы конкретных сервисов, не межролевые бизнес-процессы. Параллельность не задана, поэтому fork/join не требуется. Основа: [Анисимов, §§14.5–14.6](https://sites.google.com/site/anisimovkhv/learning/pris/lecture/tema14/tema14_3).

Ошибка доступа при GET статуса или недоступность сервера не доказывают отказ исходной команды: форма сохраняет ключ и неопределённость, пока результат нельзя достоверно прочитать. Guards автомата относятся к исходу исходной команды. Если сохранённый результат уже есть, предварительная проверка не отклоняет его только из-за более новой рабочей revision.
