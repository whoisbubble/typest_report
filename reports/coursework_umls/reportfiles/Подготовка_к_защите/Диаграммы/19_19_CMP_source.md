## Где какие элементы и что они означают

Блоки «source» подписаны apps/web, apps/api, apps/worker, packages/contracts, application, domain, persistence и ops. Внутри перечислены обязанности и примеры классов. Штриховые зависимости направлены от использующего модуля к используемому. Указание DI объясняет подключение инфраструктурной реализации через зависимость/контракт.

## Как читать нашу схему

Web содержит страницы и модели представления. API — HTTP-контроллеры и guards. Worker запускает анализ по расписанию. Contracts объединяет DTO и контракт API. Application организует сценарии; domain содержит предметные правила; persistence — ORM-сущности, репозитории и миграции. Ops содержит инструкции сборки, proxy и копирования. Проследи, где будет ImportViewModel, ImportService и таблица publications.

## Зачем именно такое решение

Клиент не должен импортировать пароль БД и код репозиториев. Разделение помогает использовать общие правила из API и worker, сохраняя заменяемый механизм хранения. Папки здесь представлены как группы исходных файлов, а не как отдельные физические серверы. Диаграмма задаёт план структуры: эти исходники пока не написаны.

## Что ещё знать по теории

Нужно отличать source/library/executable/document/table, предоставляемый и требуемый интерфейс, компонент и артефакт. В лекции есть исторические обозначения; смысл нашей группировки оговорён явно.

## Вопросы для защиты с ответами

- **Это диаграмма классов?** Нет, классы упомянуты как содержимое компонентов.
- **Что такое DI?** Передача нужной реализации зависимости снаружи вместо жёсткого создания внутри сценария.
- **Почему source?** Рассматриваются исходные модули до сборки.
- **Почему не все импорты нарисованы?** Это архитектурный уровень основных зависимостей, а не граф каждого оператора import.
