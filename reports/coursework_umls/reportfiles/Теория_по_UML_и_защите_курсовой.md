# 2.1. Варианты использования: теория и разбор

Актуальная редакция после аудита. Общие правила проекта закреплены в [согласованной спецификации](Описание_согласованной_модели.md).

## Элементы

Актор-человечек — внешняя роль, эллипс — законченная пользовательская функция. Прямоугольник отделяет систему от акторов. Сплошная линия показывает участие роли, а не порядок работы. `«include»` направляется от базовой функции к обязательной части. `«extend»` направляется от дополнительной функции к расширяемой; рядом заданы условие и именованная точка подключения. Название extension point помещено в нижнюю секцию расширяемого эллипса. Наследование здесь не требуется.

Основа нотации: [Анисимов, §§12.2–12.4](https://sites.google.com/site/anisimovkhv/learning/pris/lecture/tema12/tema12_2). Сценарии и распределение полномочий ниже — решения SMM Analyzer.

## 01. Контекст

![Контекст](images/01_UC_context.png)

Администратор управляет учётными записями и доступом. Менеджер ведёт кампании, финансы, импорт и публикацию отчётов. Аналитик анализирует данные и готовит выводы. Заказчик читает опубликованные версии своего клиента. Один человек может совмещать роли. Клиент-организация в БД и пользователь-заказчик — разные понятия.

Предусловие защищённых функций — успешная аутентификация. Сервер повторно проверяет полномочия при каждом запросе, а не только при открытии экрана. Контекст не является матрицей всех технических разрешений.

## 02. Ведение клиентов и кампаний: создание кампании

![Кампания](images/02_UC_campaigns.png)

На этой детализации раскрыт сценарий **создания и настройки кампании** внутри более широкой функции ведения клиентов и кампаний. Определение клиента, ввод параметров и назначение ответственных обязательны для этого сценария. Если клиент не найден, в точке `нетКлиента` выполняется регистрация. Простая последующая правка названия клиента — самостоятельная операция и не означает обязательного повторного назначения сотрудников.

Предусловие: менеджер вошёл в систему и имеет право управления кампанией. Основной поток: определить клиента → задать параметры → назначить сотрудников → сохранить согласованные данные. Постусловие: кампания относится к одному клиенту, назначения не дублируются. Порядок задан этим текстом, а не расположением include-стрелок.

## 03. Импорт

![Импорт](images/03_UC_import.png)

Менеджер выбирает публикацию и файл, система проверяет данные, затем сохраняет набор. Ошибки подключаются в точке `проверкаЗавершена` при условии `[есть ошибки]`; ошибочный набор не записывается как успешный. Функция include сохранения относится к основному успешному потоку, а не к требованию записать ошибочный файл.

Предусловия: доступ к кампании публикации, выбранная публикация, доступный файл. Клиент создаёт requestId до отправки. Постусловие успеха: согласованный набор и сохранённый итог запроса; повтор того же принятого ключа не создаёт новую запись данных. Сетевой тайм-аут сам по себе не означает отказ.

## 04. Отчёт

![Отчёт](images/04_UC_reports.png)

Менеджер создаёт/открывает рабочую версию отчёта. Аналитик сохраняет выводы на сервере с проверкой revision. Публикация выполняется менеджером после проверки прав, заполненности и актуальности. В точке `передПубликацией` замечания возвращают черновик на исправление. Аналитик не получает право публикации автоматически.

Основной поток: получить рабочую версию → сохранить выводы → проверить → опубликовать снимок. Альтернативы: недостаточно прав, устаревшая revision, обновившиеся источники, отсутствие выводов. После отказа рабочая версия сохраняется. После успеха опубликованный снимок неизменяем; дальнейшая работа повышает revision того же логического отчёта.

Действия аналитика и чтение заказчиком имеют продолжение в ApplicationApi на схемах 13–14; это не только текстовые обещания.

# 2.2. Автоматы: состояния, события и восстановление результата

Редакция после аудита. Основа: [Анисимов, §§12.6–12.8](https://sites.google.com/site/anisimovkhv/learning/pris/lecture/tema12/tema12_3).

## Обозначения

Скруглённый прямоугольник — состояние, в котором интерфейс может находиться некоторое время. Чёрная точка — начало, точка в окружности — завершение. Стрелка — допустимый переход. Подпись читается как `событие [условие] / действие`. `entry` выполняется при входе; `do` обозначает деятельность в состоянии. Внутренняя реакция остаётся в состоянии и не повторяет entry. Два соединённых кружка у состояния означают скрытую детализацию в отдельном автомате. Переход без события является переходом по завершении; условия завершённой проверки взаимоисключающие.

## 05. Контекст интерфейса

![Контекст](images/05_SM_context.png)

Граница — рабочая область после аутентификации. Большая рамка является составным состоянием. Меню открывает один раздел при наличии полномочия; отсутствие права обрабатывается внутренней реакцией меню. Раздел данных объединяет кампании, финансы и доступ. Просмотр объединяет аналитику и кабинет заказчика в пределах прав конкретной роли.

Импорт запускает SM_02, отчёты — SM_03. Их завершение возвращает управление в меню. Из других разделов возврат вызывается закрытием. Выход завершает сеанс только при отсутствии незавершённой операции и после решения судьбы несохранённых правок. Неизвестный итог записи тоже считается незавершённой операцией. Закрытие вкладки не отменяет уже выполненную серверную транзакцию.

## 06. Импорт

![Импорт](images/06_SM_import.png)

Форма → проверка → выполнение → показ результата — основной путь. Подтверждённый отказ ведёт к ошибкам, исправление возвращает к вводу. Для новой исправленной команды создаётся новый ключ. Для повторной отправки **той же незавершённой команды** ключ остаётся прежним.

Потеря связи переводит в «Уточняется итог запроса». Клиент вызывает getImportStatus(key). Если сохранённый итог найден, показывается результат или подтверждённый отказ. `notFound` не доказывает откат: запрос мог ещё выполняться. Разрешён безопасный повтор исходной команды с прежним ключом, но не создание новой команды с новым ключом. Если файл недоступен после перезагрузки браузера, пользователь повторно выбирает тот же файл, его хеш проверяется перед повтором.

Метаданные PendingImport сохраняют ключ, публикацию и хеш; File хранится только в памяти. Сам метод recover использует сохранённое состояние. Повторы выполняются с задержкой и не запускаются конкурентным бесконечным циклом. При недоступности сети состояние неопределённости сохраняется честно; получение окончательного результата зависит от восстановления связи.

## 07. Отчёт

![Отчёт](images/07_SM_reports.png)

В редакторе можно сохранить выводы через saveDraft и пересчитать содержимое через refreshDraft с ожидаемой revision. При конфликте сервер не перезаписывает чужие правки; форма показывает замечание и предлагает перечитать рабочую версию. Внутренние реакции не означают безусловного успеха: ошибка отображается в том же редакторе.

Публикация проходит проверку и атомарную фиксацию. Потеря ответа ведёт в уточнение итога через getPublicationStatus(key). PendingPublication хранит исходные reportId, expectedRevision и key; повтор не берёт более новую revision из случайно открытого экрана. Сервер сопоставляет ключ с конкретным пользователем, отчётом и revision. Отказ и успешная фиксация — разные события; неизвестный результат не считается отказом.

Из опубликованного результата открывается новая рабочая revision **того же reportId**. Старый снимок в report_versions не изменяется. Закрытие доступно из ввода, подтверждённых ошибок и результата. Пока исход неизвестен, штатное закрытие процесса не выдаётся за отмену записи.

Все состояния достижимы из начала и имеют потенциальный путь к завершению. Состояние ожидания не обещает гарантированного ответа при постоянно отключённой сети. Серверная проверка прав остаётся обязательной независимо от состояния кнопок.

# 3. Классы анализа, последовательности и коммуникации

## 08. Общая модель анализа

![Классы анализа](images/08_AN_classes.png)

`boundary` — формы, панели и внешние интерфейсы; `control` — управление сценариями и проверками; `entity` — долговременно сохраняемые понятия. Это укрупнённые классы, а не таблицы или готовые React-компоненты. Имя класса не подчёркнуто; на взаимодействиях имена экземпляров подчёркнуты и имеют двоеточие.

Каждый boundary связан с актором. Форма кампании, импорта, аналитики и отчёта передают работу соответствующим control. Кабинет заказчика получает только опубликованные версии через управление отчётами. Повторённые менеджеры — одна роль. «Кампания» включает связанные клиентские и финансовые сведения; «Данные публикации» — публикацию, метрики и комментарии; «Отчёт» — рабочую информацию и опубликованные снимки. На проектировании эти понятия уточнены до 14 сущностей БД.

Сплошные связи — ассоциации. Кратность 1 у кампании и 0..* у данных публикации означает одну кампанию для каждой публикации и произвольное количество публикаций кампании. Связь анализа и отчёта на проектировании реализуется сохранением снимка содержимого, без обязательной join-таблицы.

Основа: [Анисимов, §§13.2–13.4](https://sites.google.com/site/anisimovkhv/learning/pris/lecture/tema13/tema13_2).

## Как читать взаимодействия

На последовательности время идёт сверху вниз. Пунктирная вертикаль — линия жизни. Сплошная стрелка с заполненным наконечником — синхронный вызов, штриховая с открытым наконечником — ответ. Узкие активации необязательны и в новой редакции опущены для ясного чтения фрагментов. Петля — обращение к себе. Рамка alt делится на взаимоисключающие операнды `[допустимо]` и `[иначе]`.

На коммуникации сплошные ненаправленные линии связывают экземпляры, короткие стрелки рядом показывают сообщения. Время определяют номера. Условные сообщения имеют те же guards, что операнды alt. Содержание обеих пар генерируется из единого набора сообщений, а не независимо перерисовывается.

Основа: [Анисимов, §§13.5–13.8](https://sites.google.com/site/anisimovkhv/learning/pris/lecture/tema13/tema13_3). Все участники приняты существующими до и после взаимодействия; кресты уничтожения не нужны. Классы анализа не предписывают прямой доступ браузера к БД.

## Связь с реализацией

Управление импортом уточняется до ImportService.importData; управление отчётами — до ReportService.buildDraft/saveDraft/publish. Контроль безопасности и TypeORM скрыты за этими обязанностями на уровне анализа. Клиентское ожидание результата не означает, что UI должен изображать успех до подтверждения сервера.

# 4. Классы проектирования и деятельности

Актуальная редакция после аудита. Точные бизнес-инварианты, права и правила повторов находятся в [согласованной спецификации](Описание_согласованной_модели.md).

## 13–14. Клиентские классы

![Логические классы](images/13_DES_client_logical.png)

![Физические классы](images/14_DES_client_physical.png)

Прямоугольник имеет секции имени, атрибутов и операций. `−` — private, `+` — public. Сплошная стрелка показывает навигацию по хранимой ссылке. Кратность 1 у API означает один интерфейсный объект у формы; 0..* у форм допускает совместное использование адаптера. Рабочая область открывает 0..1 экземпляра каждой модели. Состояние сеанса относится к одной рабочей области. Штриховая стрелка с пустым треугольником от HttpApplicationApi к ApplicationApi — реализация интерфейса, а не зависимость и не наследование React-компонента.

Модель кампании хранит CampaignDto. Модель импорта хранит незавершённый запрос, модель отчёта — черновик и исходные параметры публикации. saveFindings сохраняет данные на сервере. PublishedReportsModel читает опубликованные версии для заказчика. ReportDraft закрывает поля и открывает операции чтения/проверки. API возвращает данные, а HTTP-адаптер создаёт из DTO объект ReportDraft с методами.

Это классы **основных рассматриваемых сценариев**, а не полный реестр всех вспомогательных форм системы. Учётные записи, справочники и финансовые экраны остаются отдельными разделами общего контекста. Размещение кода соответствует компонентам 19: модели и HTTP-адаптер — apps/web, контракт и DTO — packages/contracts. TypeScript interface описывает требования, а не содержит готовую реализацию.

Реализация HttpApplicationApi обязана поддерживать все операции контракта; в её секциях показаны только собственное состояние и общий приватный механизм HTTP-запроса. Сигнатура request<T> — сокращённое представление общего механизма; параметры метода HTTP, тела и заголовков уточняются в коде. В Drawio угловые скобки generic-типов сохранены как текст.

### Вспомогательные типы

| Тип | Определение |
|---|---|
| UUID | `type UUID = string` |
| UserRole | `admin / manager / analyst / customer` |
| Permission | Полномочия `campaign.write`, `import.execute`, `report.edit`, `report.publish`, `report.read` для этой модели |
| Section | Разделы `campaigns / imports / reports / analytics / access / customer`; финансы входят в группу данных |
| Period | `{from: string; to: string}`, календарные даты ISO YYYY-MM-DD |
| CampaignInput | `{id?: UUID; expectedRevision?: number; clientId: UUID; name: string; goal: string; startsOn: string; endsOn: string; budget: string}` |
| CampaignDto | Данные кампании с обязательными `id`, `revision: number` |
| PendingImport | `{key: UUID; publicationId: UUID; fileHash: string; file: File|null}` |
| PendingPublication | `{key: UUID; reportId: UUID; expectedRevision: number}` |
| ImportResult | `{jobId: UUID; requestId: UUID; imported: number; errors: string[]}` |
| ReportDto | `{id: UUID; reportId: UUID; version: number; draftRevision: number; publishedAt: string; snapshot: Record<string,unknown>}`; id — ID опубликованной версии |
| OperationOutcome<T> | Общий `requestId: UUID` и объединение `{state:'done'; value:T}`, `{state:'rejected'; errors:string[]}`, `{state:'unknown'}` и `{state:'notFound'}` |
| ImportOutcome | `OperationOutcome<ImportResult>` |
| PublishOutcome | `OperationOutcome<ReportDto>` |

`Promise<T>` — асинхронное получение значения, `File` — стандартный браузерный тип. Денежные значения передаются строками. После чтения исхода `done` клиент показывает успех; rejected означает подтверждённый отказ. unknown — исход неизвестен. notFound допустим у чтения статуса и не доказывает отсутствия выполняющейся транзакции.

buildDraft создаёт либо читает отчёт кампании за период. getDraft читает существующую рабочую версию; refreshDraft пересчитывает показатели с ожидаемой revision и сохраняет выводы аналитика. saveDraft меняет выводы с проверкой revision. Это устраняет тупик, при котором устаревший отчёт можно отклонить, но нельзя обновить.

Основа: [Анисимов, §§14.2–14.3](https://sites.google.com/site/anisimovkhv/learning/pris/lecture/tema14/tema14_2). Конкретный веб-стек и контракт — проектные решения SMM Analyzer.

## 15–16. Одна модель БД, три согласованных фрагмента

## 17–18. Деятельности методов

![Импорт](images/17_ACT_import.png)

![Публикация](images/18_ACT_publish.png)

Точка — начало, скруглённый блок — действие, ромб с текстом — решение, пустой ромб — слияние альтернатив, точка в окружности — конец. Каждому из трёх решений соответствует своё слияние. У исходов записи три несовместимых условия: подтверждённая фиксация, подтверждённый откат и неизвестный итог. Последний возвращает unknown, а не притворяется откатом.

После проверки личности и привязки ключа ищется сохранённый итог. Найденный результат возвращается без новой записи. Для новой команды выполняется проверка. Недопустимая команда даёт подтверждённый отказ. Допустимая — атомарную сверку и запись. Повторная проверка ключа, актуальности и доступа находится **внутри транзакционной границы**, а не только до неё. Реальное состояние БД защищают ограничения и условная запись/блокировки, а не нарисованная проверка сама по себе.

ImportService.importData(actor, publicationId, file, key) сохраняет набор, итог запроса и аудит; ReportService.publish(actor, reportId, expectedRevision, key) фиксирует снимок, ключ и аудит. Оба возвращают соответствующий OperationOutcome. GET статуса не выполняет повторную запись.

Дорожки не добавлены: это внутренние методы конкретных сервисов, не межролевые бизнес-процессы. Параллельность не задана, поэтому fork/join не требуется. Основа: [Анисимов, §§14.5–14.6](https://sites.google.com/site/anisimovkhv/learning/pris/lecture/tema14/tema14_3).

Ошибка доступа при GET статуса или недоступность сервера не доказывают отказ исходной команды: форма сохраняет ключ и неопределённость, пока результат нельзя достоверно прочитать. Guards автомата относятся к исходу исходной команды. Если сохранённый результат уже есть, предварительная проверка не отклоняет его только из-за более новой рабочей revision.

### Как читать элементы

Прямоугольник с маленьким значком компонента обозначает программный компонент. `«source»` уточняет, что это исходный код. Здесь несколько связанных файлов объединены в один компонент по папке; отдельный класс предполагается хранить в отдельном `.ts`-файле. Это помогает показать систему без десятков мелких прямоугольников.

Штриховая линия с открытым наконечником — зависимость. Её читают **от использующего компонента к используемому**. Например, `apps/web → packages/contracts`: веб-клиент использует типы интерфейса и DTO. Это не передача HTTP-запроса между запущенными серверами.

Доменный Campaign и объект CampaignEntity для TypeORM имеют разные обязанности: первый выражает правила предметной области, второй — отображение в таблицу. Это не две разные кампании в базе. Domain и persistence не должны импортировать веб-страницы.

Контракт ApplicationApi реализуется HTTP-адаптером в клиентском приложении. Общие DTO можно импортировать в оба приложения как типы; секреты и код репозиториев в браузерную сборку не включаются. На схеме показаны основные зависимости уровня папок, а не полный граф всех импортов.

## 20. Состав исполняемых компонентов системы

![Исполняемые компоненты](images/20_CMP_runtime.png)

Здесь показано то, что участвует в работе системы после сборки. Граница компонента не обязательно равна компьютеру: на сервере могут одновременно работать Nginx, Next.js, API и worker. Их размещение раскрывает следующая схема.

Внутри компонентов явно подписаны предоставляемые и требуемые интерфейсы. Интерфейс — договор о доступных операциях. `REST / JSON` означает HTTP API с сообщениями JSON; `PostgreSQL / SQL` — доступ к СУБД по её протоколу. Для интерфейсов использовано текстовое представление в секциях компонентов: отдельные кружки и сокеты на этой схеме не применяются.

**Стрелки — зависимости, а не поток данных:** backup зависит от PostgreSQL, хотя дамп при чтении поступает из БД в backup. Для ответов не рисуется обратная стрелка: они входят во взаимодействие через тот же интерфейс.

### Как проходит пользовательский запрос

1. Браузер загружает страницы и JS через единую HTTPS-точку входа Nginx.
2. Nginx направляет `/` и ресурсы в Next.js, `/api/*` — в NestJS, снимая внешний префикс `/api` согласно конфигурации.
3. API устанавливает личность пользователя, проверяет полномочия и принадлежность кампании, затем вызывает прикладной сервис.
4. Сервис работает с PostgreSQL через TypeORM. Результат возвращается пользователю по тому же каналу.

Пользователь определяется по проверенному сервером сеансу. Конкретная реализация сеанса и способ хранения токена выбираются при реализации. В проекте предусмотрены хеши паролей, проверка активного пользователя, роли и назначения на кампании. Одного скрытия кнопок в браузере недостаточно.

### Зачем отдельный worker

Worker выполняет анализ публикаций по расписанию, чтобы длительные расчёты не занимали HTTP-запрос. В начальном проекте достаточно одного экземпляра. Он читает сохранённые комментарии и метрики, записывает analysis_results. ML не обучается: интерфейс анализатора позволяет позднее подключить отдельную реализацию для ВКР; до неё возможны описательные расчёты и правила.

Для этой топологии отдельный брокер сообщений не требуется. API и worker используют PostgreSQL. Worker выбирает публикации без результата для текущей publications.data_revision; analysis_results.input_revision хранит именно её. Перед записью повторно проверяется входная версия. Собственный результат анализа не меняет data_revision, но меняет campaigns.revision для актуальности отчётов. Точные правила — в [согласованной спецификации](Описание_согласованной_модели.md).

**Это не перенос импорта из диаграммы 17 в фоновую очередь.** Сам метод ImportService сохраняет набор данных и возвращает результат согласно уже принятой деятельности. Анализ — последующая отдельная операция. Когда анализ изменяет исходные сведения для отчёта, revision кампании повышается, чтобы схема 18 могла обнаружить устаревший черновик.

### Где отчёты и копии

Черновики и опубликованные снимки находятся в reports и report_versions PostgreSQL, как в схеме 16. Отдельное файловое хранилище PDF здесь не добавляется. Архив резервных копий — другое назначение: восстановление БД после потери данных.

Резервное копирование — отдельный исполняемый служебный компонент: планировщик запускает pg_dump, дамп шифруется и передаётся по SFTP. Опубликованные отчёты не извлекаются из этого архива при обычной работе пользователя.

## 21. Общая диаграмма развёртывания

![Развёртывание](images/21_DEP_system.png)

### Что означает графика

- **Куб `«device»`** — вычислительный узел. Указаны рабочие места, сервер приложений, сервер БД и отдельное хранилище копий.
- **Вложенный прямоугольник** — установленный компонент. Вложенность отвечает на вопрос «где это работает».
- **`«executionEnvironment»`** — среда выполнения: браузер исполняет клиентский JS. Node.js и Docker подписаны у соответствующих серверных компонентов и узлов.
- **`«executable»`** — запускаемый служебный модуль; **`«artifact»`** — сохраняемый результат, здесь архив файлов.
- **Линия без стрелки** — канал обмена. На ней подписаны протокол и порт; двусторонний обмен не требует двух противоположных стрелок.
- **`[1..*]`** — один или несколько экземпляров рабочих мест. Точная численность сотрудников и клиентов пока не задана.

Это проект для одного развёртывания малого агентства, без кластеров и реплик. Все роли используют одну браузерную программу; доступные функции определяет серверная авторизация. Заказчик видит только доступные ему клиентские данные и опубликованные версии.

### Принятые места размещения

| Узел | Что установлено | Причина |
|---|---|---|
| Рабочие места | Браузер, загружаемые страницы и клиентский JS | Не требуется установка настольного клиента |
| Сервер приложений | Docker Engine, контейнеры Nginx, Next.js, NestJS, worker | Единое развёртывание кода приложения при раздельных процессах |
| Сервер БД | PostgreSQL, постоянный том pgdata, среда pg_dump с планировщиком | Данные не зависят от жизненного цикла контейнера приложения |
| Хранилище копий | SFTP-сервис и зашифрованные дампы на отдельном узле | Потеря диска основного сервера не уничтожает единственную копию |

### Каналы и ограничения доступа

| Участники | Интерфейс | Ограничение |
|---|---|---|
| Браузер → Nginx | HTTPS, TCP 443 | Единственная публичная точка входа приложения |
| Nginx ↔ Next.js | HTTP, TCP 3000 | Только закрытая Docker-сеть одного сервера |
| Nginx ↔ API | HTTP, TCP 3001 | Только закрытая Docker-сеть; публично доступен маршрут HTTPS `/api/*` |
| API/worker ↔ PostgreSQL | Протокол PostgreSQL поверх TLS, TCP 5432 | Межсерверное закрытое соединение; разрешены адреса сервера приложений |
| pg_dump ↔ PostgreSQL | libpq, TCP 5432 | Локальная служебная сеть сервера БД; отдельные права чтения |
| Среда копирования ↔ архив | SFTP поверх SSH, TCP 22 | Разрешён сервер БД и отдельная служебная учётная запись |

Канал сервер приложений — сервер БД на рисунке объединяет соединения API и worker: это один сетевой путь, но разные процессы и подключения. Внутри сервера БД библиотека libpq используется pg_dump, а не пользовательским браузером. Обратная передача ответов подразумевается.

Терминация TLS находится в Nginx. HTTP внутри одного доверенного хоста — принятое упрощение проекта, не рекомендация открывать эти порты в Интернет. PostgreSQL и SFTP не публикуются для рабочих мест. Межсетевой экран допускает только перечисленные назначения; административные SSH-подключения находятся вне рассматриваемых пользовательских сценариев.

### Резервное копирование и целостность

pg_dump формирует согласованную логическую копию. Проектное допущение: один дамп ночью с хранением последних 14 успешных копий. Реальные RPO/RTO и объём диска согласуются с агентством после появления объёма данных; сроки не выданы за требования преподавателя. Шифрование выполняется до отправки, ключ восстановления хранится отдельно от архива; проверяются контрольная сумма и успешное завершение передачи. Удаление старой копии допустимо после сохранения новой.

В план эксплуатации входит пробное восстановление в изолированную БД. Сам факт наличия файла ещё не доказывает возможность восстановления. На текущем этапе это проектная процедура: реальное копирование и восстановление не запускались.

PK/FK, CHECK/UNIQUE и транзакции из модели 16 защищают данные при записи. Для публикации сохраняются проверки revision и неизменяемая версия отчёта из схемы 18. Аудит действий находится в PostgreSQL, резервные копии дополняют эти меры, но не заменяют их. Runtime-роли БД не должны иметь права изменения схемы; миграции выполняются отдельно.

### Сборка и воспроизводимость

| Исходные компоненты 19 | Результат для схем 20–21 |
|---|---|
| apps/web + contracts | Серверная сборка Next.js и клиентский JS-пакет |
| apps/api + application + domain + persistence + contracts | Образ API NestJS |
| apps/worker + application + domain + persistence | Образ фонового обработчика |
| ops/nginx.conf | Конфигурация Nginx |
| ops/backup.sh | Служебный запуск pg_dump, шифрование, SFTP |
| persistence/migrations | Миграции таблиц PostgreSQL |
| ops/compose.yaml + Dockerfile.* | Параметры сборки и запуска контейнеров на соответствующих узлах |

Артефакты проектируются с общим тегом релиза `smm-web:<release>`, `smm-api:<release>`, `smm-worker:<release>`; `<release>` — обозначение будущего значения, а не существующая версия. Конкретные версии Node.js, PostgreSQL и базовых образов фиксируются при реализации вместе с lock-файлами и digest. Они намеренно не выдуманы в диаграмме. Для двух серверов используются отдельные конфигурации запуска, а не иллюзия, что один Docker Compose автоматически управляет удалёнными компьютерами.

## Как объяснить на защите

«Диаграмма 19 отвечает, из каких исходных модулей состоит проект и какие зависимости между ними. Диаграмма 20 показывает состав работающей системы и её интерфейсы. Диаграмма 21 показывает, на каких компьютерах размещены эти компоненты и по каким протоколам они взаимодействуют. Браузер не подключается к БД. Запросы проходят через Nginx и NestJS, фоновые расчёты выполняет worker, а резервные копии хранятся отдельно от основной БД».

Если спрашивают о стрелках: на 19–20 это зависимости «использует», на 21 линии без стрелок — каналы обмена. Компонент — часть программы; узел — место её выполнения; интерфейс — набор возможностей для взаимодействия. Куб не является таблицей БД, а компонент не является классом.
